## 1. 背景与目标（Why）

### 1.1 背景
个人 / 小团队在直连多家大模型 API 时，长期面临三件事：
- **接口碎片化**：OpenAI / Anthropic / Google / DeepSeek / 通义 / 文心 的请求格式、鉴权、流式分片各不相同，开发者每接一家都要改代码。
- **成本黑盒**：真实 API key 散落在各处，花了多少、花在哪说不清。
- **单点脆弱**：某家模型 token 额度耗尽或临时故障，应用直接报错，没有兜底。

### 1.2 问题陈述
1. 开发者接入新模型成本高（改代码适配）。
2. 成本不可归因、不可控（预算风险）。
3. 单模型额度耗尽 / 故障时服务中断，无自动切换。

### 1.3 业务目标
提供一个**统一入口**，让开发者用一组 key 透明地调用多家大模型，实现：
- 接入效率提升（改一个 `base_url` 而非改代码）；
- 成本可归因、可设额度；
- 单模型额度耗尽或故障时**自动切换到可用模型**，服务不中断。

### 1.4 成功指标
见 §7。核心北极星：**月度活跃虚拟 Key 数（MAK）**——反映统一入口是否真正被采用。

## 2. 用户与角色

| 角色 | 职责 | 是否进控制台 |
|------|------|--------------|
| **管理员（admin）** | 管理账号（创建/禁用/改角色）、配置 provider、创建与管理虚拟 key、设置路由与额度、查看全局成本与用量 | 是（全功能） |
| **普通用户（user）** | 通过分配的 key 接入自己的应用，查看自身用量 | 是（仅用量视图，无管理配置） |

> 账号体系在**项目初期即纳入**，支持简单的角色鉴权（admin / user 两种角色）。单租户，不做多租户隔离。

---

## 3. 用户故事

- 作为**开发者（普通用户）**，我希望用网关分配的 key 调用多家大模型，以便不用为每个模型改代码。
- 作为**开发者**，我希望某模型 token 额度耗尽时请求能自动切到同组可用模型，以便服务不中断。
- 作为**管理员**，我希望创建并管理账号（含角色分配），以便控制谁能使用与配置。
- 作为**管理员**，我希望为 key 设置每日额度，以便控制成本风险。
- 作为**管理员**，我希望查看按 key / 模型 / 时间的用量与成本，以便账单可解释。
- 作为**管理员**，我希望在控制台配置 provider 与路由策略（含 fallback），以便灵活调度流量。

## 4. 功能需求（范围）

### 4.1 账号与角色体系（MVP）
- 账号注册 / 登录（简单口令，初期单租户）。
- 角色：**admin / user**。admin 可创建、禁用、修改其他账号的角色。
- 鉴权覆盖：控制台页面与网关 API 均基于账号 / 虚拟 key 鉴权。
- user 无法进入管理配置页（路由、provider、账号管理）。

### 4.2 虚拟 Key 管理
- 管理员为某账号 / 用途创建虚拟 Key（VK），绑定所属账号、可选每日额度、启用 / 禁用。
- VK 明文仅创建时返回一次；入库只存 SHA-256 哈希。
- 支持列表、查看（掩码）、启用 / 禁用、删除、重置。

### 4.3 Provider 配置
- 配置多家 provider（OpenAI / Anthropic / Google / DeepSeek / 通义 / 文心 等）。
- 填写凭证引用（环境变量名，真实 key 不入库）、启停、权重。
- 支持增删改与启停切换。

### 4.4 路由与高可用（核心）
- **模型别名 → 候选 provider 列表 + 策略**（weighted / cost / failover）。一个 key 调用某别名时，背后是一组模型。
- **配额感知路由（重点需求）**：当某 provider / 模型调用因 **token 额度耗尽**（余额不足、quota 耗尽，通常表现为 `429` 或 provider 特定错误码）失败时，网关将其标记为「额度耗尽 / 暂不可用」，并自动把请求 **fallback 到同别名下另一个可用 provider**。该标记可在额度恢复（自动探测）或管理员手动重置后清除。
- **传统健康检查**：对超时 / 5xx 也做降级与 fallback，与额度耗尽共用同一条 fallback 链。
- 重试仅限可重试错误（超时 / 5xx / 429），带指数退避 + 抖动；**禁止对 4xx（除 429）重试**，避免放大故障。
- 熔断：连续失败率超阈值则短暂熔断该 provider，防重试风暴。

### 4.5 限流与配额（MVP）
- 按 **key 设置每日 token 或金额额度**；超限返回 `429` + `Retry-After`。
- 细粒度 QPS / 并发限流为**后置项**，本期不做。

### 4.6 用量与成本计量
- 每次调用记录：`vk_id, 模型, provider, prompt_tokens, completion_tokens, cost_usd, latency_ms, status, timestamp`。
- 成本按 `model → 单价` 配置表换算；**非 OpenAI 模型 token 为估算**（界面标注「估算」），关键账单以 provider 为准。
- 报表：按 key / 模型 / 日期聚合，控制台展示。

### 4.7 管理控制台（前端，形态：管理控制台）
- 登录 / 账号页
- 概览 Dashboard（今日调用量 / 花费 / 错误率）
- 虚拟 Key 管理
- Provider 配置
- 路由策略（别名、候选、策略、fallback）
- 用量 / 成本报表（按 key / 模型 / 时间）
- 账号管理（admin 专属：创建 / 禁用 / 改角色）

> 前端形态为**管理控制台**，不做终端用户聊天 / 对话界面。

## 5. 非目标（Non-goals）

- 不做终端用户聊天 / 对话界面。
- 不做多租户 SaaS（单租户，账号仅作角色区分）。
- 不做模型微调 / 训练 / 私有模型部署。
- 不做细粒度 QPS / 并发限流（MVP 后置）。
- 不做 PII 脱敏 / 内容审核 / prompt 注入防护（Phase 2 可选）。

---

## 6. 验收标准（Definition of Done）

- [ ] 开发者用 OpenAI SDK 改 `base_url` 即可调用多家模型，无需改业务代码。
- [ ] 某模型额度耗尽时，请求**自动切换**到同组可用模型，且切换成功率达标（见 §7）。
- [ ] 管理员能创建账号、创建 / 管理 VK、设置每日额度、查看用量成本报表。
- [ ] 控制台登录与角色鉴权生效，user 不能进入管理配置。
- [ ] 用量与成本可按 key / 模型 / 时间归因，非 OpenAI 模型明确标注「估算」。
- [ ] 「额度耗尽」标记可被自动探测恢复或管理员手动重置。

## 7. 成功指标与度量

### 北极星（North Star）
- **月度活跃虚拟 Key 数（MAK）**：经网关真实产生调用的 key 数，反映统一入口被采用的程度。基线 = 0（上线前），目标 = 团队内主要模型调用均经网关。

### 驱动指标（Drivers）
| 指标 | 基线 | 目标 |
|------|------|------|
| 调用成功率（不含预期 fallback） | — | ≥ 99% |
| 平均单次调用成本（USD） | — | 较直连下降 / 持平（靠路由择优 + 缓存） |
| 自动切换成功率（额度耗尽后成功切到可用模型） | — | ≥ 99% |
| 成本归因覆盖率（能归因到 key / 模型的花费 %） | 0% | 100% |

### 健康指标（Health）
- p95 端到端延迟（含 fallback 路径）
- 网关 5xx 错误率
- 配额状态误标记率（不该标耗尽却标了，目标 ≈ 0）
- 控制台可用性

## 8. 风险与依赖

- **token 计量偏差**：非 OpenAI 模型依赖近似计数，关键账单以 provider 为准。
- **「额度耗尽」识别依赖 provider 错误码准确**：需针对不同 provider 适配错误映射（429 / 特定 body），否则会漏标或误标。
- **误标记**：可用模型被错误排除 → 需提供手动重置 + 自动恢复探测（周期性探活）。
- **依赖 LiteLLM SDK** 覆盖目标模型范围；个别模型需补 adapter。
- **账号体系提前引入**增加 MVP 工作量（鉴权中间件、账号 CRUD），但避免后期返工。
