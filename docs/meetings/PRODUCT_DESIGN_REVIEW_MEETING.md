## 🎬 讨论剧本

**PM**：产品设计 v0.1 过一下。四位都在，目标是对齐前端落地范围，把悬而未决的项钉死——尤其文档 §7 自己列的"框架选型/移动端待澄清"。我先抛第一个会卡 Dev 的点。

### 议题 1：前端框架 + 要不要前后端分离？

**Dev**：文档 §6/§7 写了"建议 Tailwind + 轻量组件"，但没定框架，也没定部署形态。我们是 Python/FastAPI 后端，如果上 React 独立仓库、独立部署，就多一套构建流水线、跨域、鉴权 token 传递全要处理。MVP 我想压住这块。

**PM**：我倾向 React + Vite，开发体验和组件生态最好。但 Dev 说的部署成本我认——那折中：**单仓库，React+Vite 构建成静态产物，由 FastAPI 直接托管**，不引入独立前端服务和反向代理。一台机器一个进程，部署最简单。

**用户**：只要别让我为了看个花费还要配一堆环境就行，单进程最省心。

**QA**：同意，少一个服务少一堆集成测试。

**PM**：那决议就定为 **React + Vite + Tailwind，静态产物由 FastAPI 托管，单仓库**。

### 议题 2：移动端做不做？

**Dev**：内部管理台，桌面优先就行，移动端纯增量成本。

**用户**：我只在电脑上配置，手机上看报表这种需求没有。

**PM**：明确 **MVP 不做移动端，桌面优先，响应式非必须**。文档里"响应式非必须"措辞保留，但别花工时。

### 议题 3：每日额度"token 或 ¥"——这是个坑

**PM**：§3.1 写"每日额度（token 或金额，可留空=不限制）"。这里我自己埋了个雷：一个虚拟 Key 能路由到多家 provider，各家的价格、币种、计费单位都不同，**用 ¥ 做硬限额跨 provider 没法算准**——你不知道这次调用会落到哪家的哪个价。

**Dev**：对，而且非 OpenAI 模型 token 还是估算的，用金额硬卡会更乱。我建议 MVP **每日额度只用 token 计数**，跨 provider 通用、简单、可归因。金额/成本只做报表展示，不当成硬性限额。

**用户**：行，我本来就只关心"这个 key 今天别刷爆"，token 数够直观了。花费让我在报表里看就行。

**PM**：采纳。决议：**MVP 每日额度 = token 计数（硬限额）；成本/花费仅报表展示（软观测），不做金额硬限额。**

### 议题 4：路由策略 weighted / cost / failover 三个都做？

**Dev**：三个策略里，failover（有序优先级 + 配额感知）是 PRD 定的核心，必做。weighted 简单（权重比）也能顺手做。但 cost 策略需要每张模型的价格表，还要实时算"走哪家最省"，MVP 这套价格表和动态决策引擎是纯增量，容易超范围。

**PM**：那 MVP 砍 cost，只留 failover + weighted。cost 策略进 Phase 2。

**QA**：可以，但 failover 和 weighted 切换要在路由页明确，别让管理员懵。

**PM**：决议：**MVP 路由 = failover（有序优先级）为核心 + weighted（权重比）可选；cost 策略推迟 Phase 2。**

### 议题 5：权限——前端隐藏菜单 ≠ 安全

**QA**：我必须提一个风险：§2.1 权限矩阵写"user 左侧导航隐藏管理类菜单"，但**前端隐藏只是 UX，不是鉴权**。如果后端不按角色+所有权过滤，user 直接调 API 就能读到别人的 Key 和全局报表——这是越权数据泄露，高危。

**Dev**：对，RBAC 必须后端做。我会在网关加一层**鉴权中间件**：角色决定能访问哪些接口，user 的所有查询按 `owner_account_id` 强制过滤，拿不到别人的数据。

**PM**：这条必须写死。决议：**后端 RBAC + 所有权过滤为唯一真相源；前端菜单隐藏仅 UX 层，不得作为安全边界。QA 用例必须覆盖 user 越权调 API。**

### 议题 6：CSV 导出 / 趋势图 / "近期异常"趋势——要不要砍

**PM**：§4.5 写了导出 CSV（可选），Dashboard 提了"近期调用趋势（可选，Phase 2）"。MVP 要轻，这些"可选"容易变成"顺便做了"，拖进度。

**Dev**：建议 MVP **全砍**：CSV 导出、趋势图都 Phase 2。但 Dashboard 的"近期异常"列表（被标记额度耗尽的 provider + 重置按钮）得留——它是 §3.2 自动切换闭环里管理员手动重置的入口，属于核心流，不是花活。

**用户**：只要能一键重置被误标的 provider 就行，趋势图我不在乎。

**PM**：决议：**MVP 砍 CSV 导出与趋势图（Phase 2）；保留"近期异常"列表作为重置入口。**

### 议题 7：Provider 凭证用 env 引用，运维摩擦

**Dev**：§4.3 设计是"填环境变量名，不填真实 key"——这块安全上我点赞，密钥不落库。但代价是：新增/更换 provider 得改 env + 重启网关。对小团队可接受，但要写进文档，别到时候以为在界面填了就能用。

**QA**：而且 env 改了重启期间服务会断，发布流程要记一笔。

**PM**：那 MVP 维持 env 引用（密钥不落库、运维简单），**Phase 2 再评估加密入库**（密钥加密存储 + 热加载，免重启）。文档补一句"新增 provider 需配置环境变量并重启"。

### 议题 8：额度耗尽标记怎么自动清除（探活）

**Dev**：§3.2 说"自动探活清除"。但探活怎么做有讲究：真去发请求探，会花 token、还可能触发限流；不探又永远停在"额度耗尽"。我建议 MVP **手动重置为主**，叠加一个**低频定时探活**（比如每 10 分钟对标记的 provider 发一个 tiny completion，带冷却），探活成功就清除标记。

**QA**：误标记是验收红线——健康模型绝不能被判成耗尽。我这边用 mock provider 造"真耗尽"和"健康"两种场景端到端验，误标记率目标 ≈ 0。

**用户**：探活频率别太高，别为了探活把我额度探没了（笑）。

**PM**：决议：**MVP 手动重置为主 + 低频定时探活（带冷却，tiny 调用）自动清除；误标记率目标 ≈ 0，QA mock 端到端覆盖。**
