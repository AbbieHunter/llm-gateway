## 🎬 会议实录

**PM**：M4 计划 v0.1 覆盖 US-M4-01~05 五条 Could 故事（语义缓存 / cost 路由 / CSV / 可观测面板 / PII 护栏），9 条草案 R-arch-1~9。M4 是 Phase 2 可选层，目标是在不动 MVP 主路径的前提下给网关"更省、更可运维、更合规"。今天把最容易返工或踩合规红线的点拍实。Dev 先开刀。

### 议题 1：语义缓存分层与确定性请求

**Dev**：分层本身（Tier1 精确永远先查、Tier2 语义仅在 miss 后查）没问题，和 M3 精确缓存不冲突。但我看到个计划没兜住的洞——**`seed` 请求是确定性的**：用户用固定 seed 是要对"自己那段确切措辞"复现输出。两条不同措辞、语义相近、但都带同一个 seed 的请求，如果用语义缓存把 A 的回答喂给 B，B 拿到的就不是它 seed 该给的结果，直接破坏可复现性。

**QA**：对，确定性请求不能被软复用。建议语义缓存遇到 `seed` 存在时直接跳过。

**PM**：决议：**R1 — 语义缓存作为 Tier2，精确缓存（Tier1）永远先查；`seed` 存在时跳过语义缓存（确定性请求不软复用）；T-01 验收补"带 seed 的相似 prompt 不命中语义缓存、仍走上游"**。

### 议题 2：Embedding 抽象与失败容错

**Dev**：§2.1 默认 OpenAI `text-embedding-3-small` 经 LiteLLM，测试用 fake embedding，没问题。但 embedding 调用本身也可能挂（embedding provider 限流/宕）。这条链路若失败，不能把整个请求搞挂。

**QA**：同意，语义层是"软降本"，失败必须优雅降级，不能比没有它还差。

**PM**：决议：**R2 — Embedding 抽象可插拔，默认 OpenAI 经 LiteLLM，测试用 fake；embedding 调用失败（provider 宕/限流）→ 跳过语义层直接走上游，绝不阻断请求；向量随缓存响应同条目存 Redis**。

### 议题 3：相似度阈值与检索作用域

**Dev**：默认 0.92 可配、暴力余弦，个人规模够用。但**作用域写的是 `(alias/model)`——这个有歧义**。一个 alias 下挂着多个 provider/model，deepseek 的回答和 openai 的回答对同一 prompt 不一样；如果把 deepseek 缓存的回答喂给解析到 openai 的请求，就是答非所问。语义缓存作用域必须精确到**具体模型字符串**，跨模型绝不串。

**QA**：还要加"近义不同任务"回归用例，光有"相似命中"不够。比如"把下面的中文翻译成英文" vs "总结下面这段中文"——措辞都像"处理下面这段文字"，但任务完全不同，必须不命中。

**PM**：决议：**R3 — 相似度默认 0.92 可配，暴力余弦；作用域精确到 `(provider/model)` 字符串，绝不跨模型复用；仅非流式；QA 增"近义不同任务"对照用例（如翻译 vs 总结）确保不误命中**。

### 议题 4：单价表存储形态

**Dev**：`model_prices` 表 + 种子 JSON + Admin 覆盖，OK。但计划里列了 `effective_from` 想做历史价。MVP 没必要维护价格时间线，多一列空着反而乱。

**PM**：决议：**R4 — `model_prices(provider, model, in_usd_per_1k, out_usd_per_1k, currency=USD, effective_from)`；MVP 仅用最新一行（`effective_from` 留列但暂不维护历史）；种子内置基准价 + Admin 可覆盖；仅 USD，不做多币种**。

### 议题 5：cost 策略排序与缺失价处理

**Dev**：`strategy` 增 `cost`、配额过滤后按 预估成本=单价×估算 token 排序，没问题。但有个边界——**某候选单价缺失**（新模型没进种子表），它成本算不出来。不能因为它"未知"就把它整个踢出候选（那可能踢掉唯一健康可达的），也不能把它当免费排最前。

**QA**：缺失价的候选应该"保守排后"——优先选有价的更便宜者，但未知价的仍可作为兜底被选中。同价怎么排？

**Dev**：同价按原 failover 优先级 tie-break，行为可预期。

**PM**：决议：**R5 — `model_routes.strategy` 增 `cost`；配额过滤后按 预估成本 排序选最便宜健康候选；单价缺失候选视为"未知成本"，排在有价候选之后但仍可兜底选中（不全排除）；同价 tie-break 按原 failover 优先级；仍受 `quota_exhausted`/熔断约束**。

### 议题 6：CSV 导出与安全上限

**Dev**：`format=csv` 扩 `/api/usage`，90 天/100k 上限，RBAC 复用，OK。两个补充：① 导出可能吐 100k 行，同步生成会卡事件循环，建议丢线程池；② **CSV 公式注入**——单元格以 `= + - @` 开头时，Excel/Sheets 会当成公式自动执行，虽然用量报表里模型名/Key 一般不会，但 provider 或自定义维度字符串理论上可能，得转义。

**QA**：公式注入是真实风险，尤其报表若以后带"备注/标签"类用户自由文本列。转义要做。

**PM**：决议：**R6 — `GET /api/usage?format=csv` 按当前 `group_by`+`range` 序列化；最大 90 天 / 100k 行，超限 400；RBAC 越权 403 复用；新增 CSV/公式注入防护（单元格首字符为 `= + - @` 时前缀制表符转义）；大文件生成走线程池避免阻塞事件循环；不做邮件/Excel/趋势图**。

### 议题 7：可观测面板暴露边界

**Dev**：`prometheus-client` 纯 Python，3.13 兼容；踩坑则自写零依赖 `/metrics`（计划已留兜底）。指标对齐 §4.8。两点：① 打点必须用廉价 counter/histogram，热路径不做重计算；② `/metrics` 默认开放给 Prometheus 抓，但**绝不能泄露 VK、PII、密钥**——只暴露聚合计数。

**QA**：另外 `/metrics` 最好给个开关，某些部署不想暴露。

**PM**：决议：**R7 — `prometheus-client`（踩 3.13 坑则自写零依赖 `/metrics`）；指标对齐 §4.8；打点用廉价 counter/histogram，热路径零重计算；`/metrics` 默认开放抓取但仅含聚合计数，绝不暴露 VK/PII/密钥；提供 `METRICS_ENABLED` 开关可关；提供 `docs/grafana/dashboard.json` + `prometheus.yml`，不内置 Grafana**。

### 议题 8：PII 护栏合规与流式限制

**用户**：PII 是合规红线，默认关我认同。但有个坑——**出站（模型回复）做 PII 掩码会把模型合法输出搞坏**。比如用户让模型"生成一组测试手机号"，掩码后返回 `[REDACTED]` 就废了。出站掩码不能默认开。

**Dev**：同意。入站（用户请求里的 PII）脱敏相对安全，可选替换或仅检测；出站应该默认"仅检测+可选审核"，真要掩码是更严的独立开关、默认关。还有**流式**：响应是一个个 token 吐的，逐 token 做 PII 检测/掩码很难保证不撕裂词（比如身份证号跨 chunk），出站审核在流式下只能 best-effort。

**QA**：那流式场景的出站护栏要写进 Non-goals 当已知限制，不能假装能做。

**PM**：决议：**R8 — PII 护栏默认关闭、全局 `GUARDRAILS_ENABLED` + 按路由覆盖；入站可"脱敏替换/仅检测"，出站默认"仅检测+可选审核"，出站掩码为独立更严开关、默认关（避免破坏模型合法输出）；**流式场景：仅入站脱敏生效，出站审核 best-effort 于 chunk 边界、明确为已知限制写入 Non-goals**；绝不落库原始 PII，日志/用量归因仅在脱敏后；本地正则默认（邮箱/手机/身份证），可插拔审核 API；若后续做多租户需补 DPIA（当前单/小团队自用，范围窄，文档标注）**。

### 议题 9：执行顺序与是否全做

**Dev**：5 条相互独立、可裁剪。CSV(S) 最轻，先拿 quick-win；可观测面板(M) 运维价值高且独立，紧随；cost 路由(M) 依赖新表但逻辑不重；语义缓存(L) 和 PII(L) 最大，排后面摊薄风险。

**用户**：如果哪天我们要拿这个网关处理外部用户数据，PII 就不能排最后。但眼下自用，按你说的顺序没问题。

**PM**：决议：**R9 — 确认 5 条全做（任一可裁剪不影响其余）；执行顺序 CSV(S) → 可观测面板(M) → cost 路由(M) → 语义缓存(L) → PII 护栏(L)；若合规有硬 deadline，PII 提前至可观测面板之后；语义缓存与 PII 为 L，建议拆子任务或排期靠前以摊薄风险；quick-win = CSV + 可观测面板**。
