# PRD 评审会议纪要 — LLM Gateway

> 日期：2026-07-23
> 形式：模拟评审（产品 / 开发 / 测试 / 用户 四方）
> 评审对象：PRD v0.1（范围已对齐草稿）
> 目标：确认 MVP 范围与技术风险，决策是否进入产品设计阶段

## 一、讨论要点

1. **账号体系（MVP 范围）**
   - 开发顾虑：初期即做 admin/user + 登录，比"单人免登录"多出登录、会话、账号 CRUD、权限中间件。
   - 用户立场：需给组内同事开账号（拿 key、看自身用量），管理配置自己来；要但别太重。
   - 结论：MVP 做**轻量账号**（口令登录、不做第三方/复杂注册），user 仅用量视图，无管理配置权限。

2. **高可用：token 额度耗尽 → 标记 → 自动切换（核心功能）**
   - 开发风险："额度耗尽"识别依赖 provider 错误码，各家不一致（OpenAI 余额不足多为 401、DeepSeek/通义可能 429 或独立 quota 接口），与限流 429 易混淆，需做错误码映射表。
   - 用户强诉求：曾被某家额度耗尽坑过半夜改配置，自动切换是刚需；但**健康模型不能被误标记**。
   - 测试要求：用 mock provider 模拟额度耗尽做端到端验证，误标记率目标 ≈ 0。
   - 结论：MVP 先覆盖 **OpenAI / DeepSeek / 通义** 错误码映射；fallback 链必做（额度耗尽与超时/5xx 共用）；提供**手动重置 + 自动探活恢复**；测试用 mock 端到端验证。

3. **限流（按 key 每日额度）**
   - "每日"按**本地时区自然日**重置；超限返回 `429` + `Retry-After`。细粒度 QPS 限流后置。

4. **用量成本计量（非 OpenAI 估算）**
   - 非 OpenAI 模型 token 为估算（LiteLLM token_counter 近似，长文本偏差几个点）。
   - 界面**明确标注"估算"**；额度扣减以实际返回 token 优先，估算不用于硬性扣减；关键账单以 provider 为准。

5. **前端控制台（MVP 页面）**
   - MVP 页面：**Dashboard + 虚拟 Key 管理 + Provider 配置 + 路由策略 + 用量/成本报表**；账号管理简化（可与 Key 管理合并视图）。
   - 不做花哨，优先把"建 key → 绑额度 → 配路由"核心流做顺。

6. **指标（北极星 MAK）**
   - MAK 定义：当月至少一次成功调用的虚拟 Key。埋点简单，开发+测试落实。

## 二、决议

- **PRD v0.1 评审通过**，进入产品设计阶段（前端信息架构与核心流程）。
- MVP 范围与以上六项结论一致；非目标保持不变。
- 三项技术风险列入**实现前待办**：
  1. provider 错误码映射表（OpenAI / DeepSeek / 通义 优先）；
  2. fallback / 误标记的端到端 mock 测试；
  3. 估算标注与额度扣减策略（实际 token 优先）。

## 三、行动项（Action Items）

| 角色 | 事项 |
|------|------|
| 产品 | 输出管理控制台产品设计（信息架构 + 核心流程） |
| 开发 | 调研 OpenAI / DeepSeek / 通义 额度耗尽错误码；评估 LiteLLM 是否已归一化 |
| 测试 | 编写 fallback / 误标记 测试用例（mock provider） |
| 用户 | 提供常用 provider 列表与典型调用场景，供产品设计参考 |
